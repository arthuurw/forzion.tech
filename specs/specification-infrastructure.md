## NGINX / ROTEAMENTO
- **Borda ÚNICA** (`docker-compose.edge.yml`, projeto `-p edge`): 1 só nginx binda `80/443` na VM e serve homolog + prod, roteando por `server_name`. Anexa às DUAS redes external (`forzion-hmg`+`forzion-prd`); upstreams por alias (`backend-hmg`/`frontend-hmg`, `backend-prd`/`frontend-prd`, `pact-broker`). Config = checkout de homolog (§ISOLAMENTO/EDGE). Reload = `scripts/reload-edge.sh`.
- `nginx/nginx.conf` (bind-mount ro). `:80` → 301 https (+ `/.well-known/acme-challenge/` p/ ACME). `:443` TLS (Let's Encrypt). `default_server` = `ssl_reject_handshake on` / 444.
- `location /webhooks/` → `backend-{hmg,prd}:8080` (ANTES de `location /`). Necessário p/ headers `svix-*` crus (webhooks **Stripe** e **Resend**). NÃO usar o proxy SPA `/api/backend` p/ webhook (descarta headers). Ver [specification-email].
- `location /internal/` → `return 404` (ANTES de `location /`, F3/REQ-F3.2), nos dois vhosts. Fecha o caminho DIRETO aos endpoints internos. O caminho BFF é fechado no PRÓPRIO proxy Next desde 2026-08-08: `/api/backend/internal/*` responde 404 sem encaminhar (segmento decodificado em laço + case-insensitive). Os crons batem nesses endpoints por DENTRO da VM via `docker compose exec backend curl localhost:8080/internal/...` (§Workflows billing/cron).
- `location /` → `frontend-{hmg,prd}:3000` (proxy + ws upgrade). Backend NÃO tem outra rota pública.
- **X-Forwarded-* / ForwardedHeaders**: nginx envia `X-Forwarded-For`/`-Real-IP`/`-Proto`; o backend confia via `app.UseForwardedHeaders` (Homolog/Production, `RouteBuilderExtensions.UseApiConfiguration`, antes de Auth/RateLimiter). `ForwardLimit=1` + `KnownIPNetworks` vindo de **`ForwardedHeaders__KnownNetworks`** (CSV de CIDR, `.env` da VM → `docker-compose.{server,homolog}.yml`): peer fora dessas redes tem o XFF ignorado. O proxy BFF do Next emite `X-Forwarded-For` com o IP real desde 2026-08-08, então o backend particiona o rate-limit pelo cliente e não pelo container `frontend` ([specification-security §4]).
- 🔴 **PRÉ-CONDIÇÃO DE DEPLOY — `FORWARDED_KNOWN_NETWORKS` no `.env` ANTES de subir o backend**: sem ela o boot FALHA em Homolog/Production, por desenho. Os `.env` (`/opt/forzion/.env`, `/opt/forzion/prod/.env`) são mantidos À MÃO na VM — nenhum workflow os gera. Valor = subnet das redes docker: `docker network inspect forzion-prd -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}'` (idem `forzion-hmg`). Formato/exemplo em `.env.example`. **Subnet ERRADA não quebra o boot** — a lista não está vazia — mas faz o XFF ser ignorado e devolve o rate-limit ao balde global sem sinal; validar pós-deploy que um 429 de teste atinge só o IP que abusou ([specification-security §8]).
- Server `pact.homologacao.forzion.tech:443` → `pact-broker:9292` (usa cert do domínio principal até `certbot --expand`).
- **X-Robots-Tag**: só o server block `homologacao.forzion.tech:443` injeta `add_header X-Robots-Tag "noindex, nofollow" always;` — homolog é host público, evitar indexação. NÃO replicar no server de produção (prod DEVE ser indexável). Defesa em profundidade com `robots.ts` env-gated. Ver [specification-security §3] / [specification-seo §4.1].
- **`server_tokens off`** no contexto `http` desde 2026-08-09 — banner `Server: nginx/<versão>` não é mais exposto (efetivo a partir do próximo deploy de `homolog`, borda compartilhada).
- **Doc de API não é exposta pela borda**: backend só serve OpenAPI/Scalar em Development; nenhum server block proxya `/openapi`. Tipos do harness frontend são gerados de instância local via `npm run openapi:sync`.
- **access_log em arquivo (pré-requisito do fail2ban)**: nginx loga acesso em `/var/log/nginx/access.log` (combined), exposto no host via bind-mount `/var/log/forzion-nginx:/var/log/nginx` (`docker-compose.edge.yml`) — stdout do container (json-file) NÃO serve pro fail2ban tailar. `scripts/setup-vm.sh` instala fail2ban e copia `infra/fail2ban/{filter.d/forzion-nginx-auth.conf,jail.d/forzion.local}`. Jail, limiares e rationale: [specification-security §4]. **Ban não testado em runtime — validar na VM (`fail2ban-client status forzion-nginx-auth`).**

## SSL (Let's Encrypt / certbot)
- Bootstrap UMA VEZ por ambiente: `scripts/init-ssl.sh <email> <dominio> [dominio...]` (multi-`-d`; 1º domínio = nome do dir do cert). Homolog: `... homologacao.forzion.tech pact.homologacao.forzion.tech`; prod: `... forzion.tech www.forzion.tech app.forzion.tech`. Duas vias: **edge JÁ no ar** → emite via webroot do edge SEM parar a borda (zero downtime) + `nginx -s reload`; **edge fora** (1º cert do ambiente) → nginx HTTP-only efêmero só pro desafio ACME, depois operador/deploy sobe stack + `reload-edge.sh`. `EDGE_DIR` (default `/opt/forzion/app`) = dono da config.
- Renovação: container `certbot` em loop (`certbot renew` a cada 12h) no `docker-compose.edge.yml`. Volumes: `certbot/conf` (certs), `certbot/www` (webroot ACME).
- **INVARIANTE cert eager no parse**: `nginx -t` (gate do deploy) **FALHA** (`cannot load certificate`, exit≠0) e o nginx **NÃO sobe** se `ssl_certificate` aponta p/ arquivo inexistente. Na borda ÚNICA isto é failure domain compartilhado: um `:443` de prod com cert faltando derruba o nginx que serve homolog TAMBÉM. Por isso um vhost novo só é habilitado DEPOIS do cert existir. O acoplamento por UPSTREAM (mesma classe: `host not found in upstream`) foi eliminado pelo `resolver` em runtime (§ISOLAMENTO) — o de CERT permanece. Cobertura: `scripts/test/edge-prod-isolation-check.sh`.

## DNS DE PRODUÇÃO
Zona `forzion.tech` (hPanel) apontada pra VM (`2.24.104.224`), cert emitido, cutover concluído 2026-08-06: stack `prd` no ar, `:443` de prod ativo, `forzion.tech`/`www`/`app` servindo 200, `robots.txt` indexável (homolog segue `Disallow: /` + `X-Robots-Tag`), `pk_live_` congelado no bundle de prod e `pk_test_` só em homolog.
- **Registros**: `forzion.tech`/`www`/`app` A→VM; TXT `_dmarc` com `rua`+`fo=1`. AAAA do apex **removido**.
- **GOTCHA AAAA "órfão" que na verdade é real (CANÔNICO)**: o AAAA do apex apontava pra um IPv6 que a VM de fato TEM em `eth0` (`ip -6 addr show scope global` NÃO vem vazio — não era leftover de parking). Removido mesmo assim porque `nginx/nginx.conf` não tem NENHUMA diretiva `listen [::]` em server block nenhum ⇒ nginx só binda IPv4 e cliente IPv6-first bateria em porta fechada (mesma classe do gotcha WARP/connection-refused, §ACESSO EXTERNO/WARP). **Checar só a INTERFACE não basta pra decidir manter um AAAA — precisa confirmar que o PROCESSO escuta nela.** Dual-stack de verdade (`listen [::]:80`/`:443` em cada server block + ufw/ip6tables) segue não feito.
- **Emissão do cert**: usar `scripts/init-ssl.sh` (§SSL), **NÃO** `certbot` bare-host — `/var/www/certbot` só existe DENTRO do container certbot (volume-mounted); o comando genérico de tutorial (`certbot certonly --webroot -w /var/www/certbot ...` direto na VM) falha com `does not exist or is not a directory`.
- **Paridade de headers entre vhosts**: o `location /` de prod nasceu sem `proxy_set_header X-Forwarded-Proto $scheme;` (homolog tinha). Ao criar/editar vhost, conferir a paridade dos `proxy_set_header` — divergência silenciosa quebra reconstrução de URL/scheme no backend.

## FIREWALL (ufw)
- **Provisionamento**: `scripts/setup-firewall.sh` (idempotente, standalone) é a fonte canônica das regras: `default deny incoming` + `default allow outgoing` + allow `22/80/443` + `--force enable`. `setup-vm.sh` o invoca (guard `if [ -f ... ]`). Standalone+idempotente ⇒ roda sozinho na VM viva (`ssh ubuntu@<IP> 'bash -s' < scripts/setup-firewall.sh`) sem re-executar o setup-vm inteiro.
- **Caveats das regras** (rationale aqui, não em comentário no script — regra 9): (a) os `allow` vêm ANTES do `enable` — o script chega via SSH:22; habilitar `deny incoming` sem liberar a 22 cortaria a própria sessão; (b) `--force` porque `ufw enable` é interativo (y/n) e `bash -s` non-interactive travaria; (c) o script de provisão abre a 22 PÚBLICA de propósito — nunca embutir lockout na provisão; o fechamento pro tailnet é passo manual posterior, já EXECUTADO (§DEPLOY MANUAL porta-22). **Reprovisionar do zero reabre a 22: refazer o fechamento depois.**
- **Deploy via tailnet segue OK**: quem sustenta o SSH do CI é `allow in on tailscale0` — regra por INTERFACE, cobre qualquer porta vinda do tailnet (SSH:22 + Pact broker:443) sem regra por porta. fail2ban coexiste (chains iptables próprias). Tailscale: `default allow outgoing` cobre o WireGuard de saída; conexão direta nó-a-nó pode cair pro relay DERP sob ufw (fallback transparente).
- **⚠️ GOTCHA ufw NÃO filtra portas publicadas pelo Docker** (CANÔNICO): Docker escreve regras próprias na chain `DOCKER-USER` (avaliada ANTES do `INPUT` do ufw) ⇒ container com `-p` no host fica acessível MESMO com `ufw deny incoming`. Hoje **só o nginx do edge publica** (80/443) — backend/frontend/pact de hmg e prd ficam nas redes Docker internas — então a exposição efetiva é 80/443 (+22 só no tailnet), e o ufw protege de fato APENAS serviços de HOST não-Docker. A frase "firewall 80/443-only" (§ISOLAMENTO) é garantida pelo **que está publicado**, não pelo ufw. Se publicar via `-p` algo que deveria ser privado, ufw não segura → usar regra `DOCKER-USER` (`ufw-docker`) ou bind `127.0.0.1:porta`.
- **Impacto de editar os scripts é ZERO na VM viva**: provisionamento é one-time; mudança só vale em provisão FRESCA (VM nova / 2ª VPS DR) OU rodando `setup-firewall.sh` à mão.

Pós-ação re-checa o hash e ABORTA vermelho se ainda divergir. **Reload OBRIGATÓRIO no warm**: `proxy_pass` com hostname literal resolve UMA vez no load e CACHEIA o IP — sem reload um backend recriado (IP novo) vira 502; reload graceful = zero drop. **Cold pula o reload**: o `up -d` já sobe com config/IPs novos, e um `reload` logo após o start corre com a escrita do `nginx.pid` → falso erro sob `set -e`.
  - **GOTCHA inode — edge servindo config VELHA**: bind-mount de ARQUIVO único (`./nginx/nginx.conf:/etc/nginx/nginx.conf`) prende o inode que existia no start do container. `git pull` troca o arquivo por RENAME → o container segue lendo o inode antigo, `nginx -s reload` relê essa cópia morta e `up -d` não recria (definição do serviço inalterada). Pior: o `nginx -t` roda em container EFÊMERO (mount novo) → aprova a config NOVA enquanto a viva continua velha, com o deploy VERDE. Daí a comparação de `sha256sum` + `--force-recreate` acima. Repro + gate: `scripts/test/edge-config-freshness-check.sh`.
- **Failure-domain compartilhado (custo do edge único)** — ACEITO conscientemente:
  - **Deploy**: config quebrada / cert faltando derrubaria a borda de AMBOS. Mitigações: (a) `:443` de um ambiente só é habilitado depois do cert existir (§SSL); (b) `reload-edge` valida em container efêmero ANTES de tocar no edge no ar (config ruim aborta o deploy, borda intacta; e um `nginx -s reload` ruim mantém os workers antigos).

Trade-off aceito: resolução por request (TTL 10s) troca fail-fast no load por 502 em runtime. Prova: `scripts/test/edge-resolver-check.sh` (literal reprova × variável passa, `$request_uri` preservado, upstream ausente = 502 com borda de pé).

- **Pré**: User Secrets do projeto `forzion.tech.Api` preenchidos (`ConnectionStrings:AppConnection` com `Search Path=develop`, `Auth:JwtSecret`, `Stripe:*`, `Seed:*`) — `dotnet user-secrets list --project forzion.tech.Api`.
- **GOTCHA launch-profile**: `dotnet run` puro pega o profile `http`/`https` do `launchSettings.json`, que **força `ASPNETCORE_ENVIRONMENT=Homolog`** (não Development). Pra rodar Development, bypassar o profile e setar env+URL na mão:
  ```powershell
  $env:ASPNETCORE_ENVIRONMENT="Development"; $env:ASPNETCORE_URLS="http://localhost:5230"
  dotnet run --project forzion.tech.Api --no-launch-profile
  ```
  Backend sobe em `http://localhost:5230`. (HTTPS :7220 só vale via profile `https`, que é Homolog — evitar p/ não lidar com cert dev.)
- **Frontend** precisa de `frontend/.env.local` (gitignored; NÃO commitar) — sem ele o proxy aponta p/ o default `https://localhost:7220`, que não casa com o backend HTTP:
  ```
  API_BASE_URL=http://localhost:5230          # proxy Next /api/backend + /api/auth/* → backend
  JWT_SECRET=<MESMO valor de Auth:JwtSecret>  # /api/auth/me valida a assinatura do JWT
  JWT_ISSUER=forzion.tech
  JWT_AUDIENCE=forzion.tech
  NEXT_PUBLIC_API_BASE_URL=/api/backend
  ```
  Subir: `cd frontend; npm run dev` → `:3000` (ou `npm run dev -- -p 3001` se `:3000` ocupado — `next dev` NÃO migra de porta sozinho no Next 16; falha `EADDRINUSE`).
- **Verificar**: `/health` 200 (liveness), `/health/ready` 200 (conexão Supabase OK). Admin = `Seed:AdminEmail`/`Seed:AdminPassword` do User Secret (pré-verificado pelo seed → login direto).
- **Cross-check Docker**: a stack `docker-compose.yml` é o caminho alternativo (PG local schema `develop`, sem tocar Supabase) — frontend :3001, ver [specification-local-ci-repro] §4.

## ACESSO EXTERNO / WARP
- **Sintoma + causa**: `connection refused` ao abrir `homologacao.forzion.tech` **só via Cloudflare WARP** (direto OK). Falha isolada ao egress WARP→AS47583 Hostinger (`2.24.104.224`), não ao código/VM (TCP 443/80 abertos, cert LE OK, nginx/VM logs limpos fora WARP). Causa provável: client WARP stale (RST local) ou proteção upstream Hostinger nos egress CF compartilhados. Descartados (não reinvestigar): IPv6/AAAA, DNS, origem, ufw.
